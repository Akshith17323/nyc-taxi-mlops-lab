# S9: agent-to-agent, a stretch (Day 2, 17:45–18:15, if there's time)

**Goal:** decide whether this system needs a second agent at all, and if it does, what it owns. A2A (the Agent2Agent protocol) lets agents with different owners call each other through published agent cards. It earns its complexity only when there are two owners.

## Recall check (5 minutes, no agent)

1. What's the difference between a tool (MCP) and another agent (A2A)? Who decides what each one does?
2. What would an agent card advertise, and who would read it?

## The question

Today you have one agent: the support assistant, owned by the product team, with three tools behind MCP. Somebody proposes an "ops agent" that the assistant can ask "is anything degraded right now?", and that on-call can ask too. It would read the status artifacts, Grafana, Dagster and the canary results.

## Build (only if you decide it's justified)

- An agent card (`/.well-known/agent-card.json`): its name, its one or two skills, and who owns it.
- A minimal ops agent on the app host that answers one skill from data you already have, such as `scripts/health.sh`'s view of the system or the newest status artifact.
- The assistant calling it, for one kind of rider question ("is the app having problems?").

## Decision point (one record in `decisions/`)

- **Is a second agent justified?** Name the owner it would have, the question it answers that a tool can't, and the cost: another service to run, another trust boundary, another prompt-injection surface. "No" is a fine answer; defend it.

## Done when

- Your record exists, with a yes or no and the reason.
- If yes: the agent card is served, and one assistant answer used it (visible in the trace).
